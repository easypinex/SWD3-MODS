# 蚩尤契約早期提案（已被後續研究取代）

> 原位於共用 BALANCE-RESEARCH.md。以下保留早期設計與當時待測事項，不是現行建議。wrapper 路徑已否決、靜態新卡已有後續證據；現行結論見[原生靈契](../../../docs/knowledge/native-capture-and-eligibility.md)。

### 蚩尤「15% 特別契約」的可行做法

**專案建議，尚未實作：**

1. 只在 `MOD_CARD_CHALLENGE` 戰場、白名單目標、`currentHP * 100 <= maxHP * 15` 時，包裝 `Function.CheckObsolt` 回傳可捕捉結果；其餘所有原版戰鬥完整呼叫原函式。
2. 以隔離探針先驗證 wrapper 的回傳值確實控制原生靈契 UI／成功流程，再接正式功能。不可只改選單文案或在死亡 callback 猜測結果。
3. 原生成功後，以「開戰前背包數量 → 成功後確認新增」保護流程，移除原生新增的敵人 ID，再用 `ItemClass.AddItem` 只加入一張新的 `MOD_蚩尤契約卡`。這延續目前收妖去重的安全模式。
4. 新卡使用未占用 ID、自己的 StringDB 名稱、`IT_12=true`、非 `IT_06`，並複製需要的敵方戰鬥資料；但護駕主動效果／SP 消耗要另行設計，不能自動沿用首領的敵方 AI 技能。
5. 絕不原地修改 `GameData.ItemTemp[46]`。那會同時改變劇情敵人、原版獎勵與未驗證的存檔路徑。

技術上，建立獨立卡範本是合理路徑；但「runtime 新 ItemTemp ID 是否能完整支援物品圖示、背包、靈契與存檔」尚無實測，必須先做一張無戰鬥獎勵的隔離測試卡。第一版只應支援蚩尤一張，不要同時為 97 個非卡敵人批量自動生成資料。

## 6. 後續驗證順序

1. **傷害／抗性探針**：在獨立存檔用已知技能記錄攻擊前後 HP，分別測光、雷、暗、物理、雷公鎚／暗黑魔樽、天雷聚陽鼎與金鐘罩；得出實際公式或至少可重跑的倍率表。
2. **戰力矩陣實測**：標準化 Lv60 存檔，分別測 1、2、3、5 隻蚩尤；記錄勝率、回合數、補給使用、HP／MP／SP、封魔、死亡原因與獎勵。
3. **靈契探針**：只記錄 `CheckObsolt` 的輸入／原回傳與原生 UI 是否讀取 wrapper；先不發卡、不改敵人資料。
4. **新卡探針**：確認唯一 ID、中文名稱、物品圖示、背包新增、重新讀檔、召為護駕、再次進自由挑戰、停用 MOD 後的存檔安全。
5. 完成上述證據後，再決定五隻蚩尤是實驗模式、契約模式或正式賞金內容。
